# Матеріали для пояснювальної записки

## Архітектура

Система складається з Spring Boot backend, окремого браузерного frontend і CLI-клієнта. Backend приймає документи з UTF-8 каталогу, будує індекс, виконує REST/ WebSocket пошук, а в LLM-режимі звертається до Ollama. Frontend і CLI є клієнтами API та не дублюють алгоритми індексації.

Основні шари: `document` (Document, DatasetLoader, DatasetPathResolver), `text` (Tokenizer), `index` (структура індексу і побудова), `search` (пошук і snapshot), `controller/dto` (REST), `ollama` (query expansion), `websocket` (прогрес пошуку).

## Власний інвертований індекс

Індекс — це масив `Bucket[]`, індекс bucket обчислюється через `floorMod(term.hashCode(), bucketCount)`. У bucket зберігається список `TermEntry`, тому колізії розв'язуються separate chaining без Map. Кожний `TermEntry` володіє `PostingList`; posting list підтримує відсортований список ID, бінарний пошук позиції вставки та унікальність документів. Операція пошуку копіює IDs у незалежний набір.

## Паралельна індексація

Перед worker-запуском усі document ID реєструються й перевіряються на дублікати. Документи розподіляються між N задачами циклічними позиціями. Worker токенізує свій документ і записує терміни в bucket. Синхронізація локальна для bucket, а posting list додатково захищає власний масив списку.

`CustomThreadPool` має власну blocking queue і worker threads, а не делегує виконання `Executors`. `shutdown` дає черзі poison-завдання після вже поданих задач; `shutdownNow` перериває workers і повертає невиконані задачі. `IndexBuilder` очікує completion усіх задач, обробляє `ExecutionException`/`InterruptedException` і завжди зупиняє пул.

## Snapshot і узгодженість

Кожна перебудова працює з новим `InvertedIndex`. Поле `volatile BuildSnapshot` змінюється одним присвоєнням після успішної побудови. Отже, пошук, що вже почався, продовжує працювати зі старою повною версією, а помилка worker або читання не публікує частковий індекс. `SearchService` зберігає узгоджені разом snapshot, документи та статистику.

## Експеримент

`ExtendedPerformanceScenario` використав 500/2000/5000/10000 документів, 150 токенів на документ, vocabulary 1000, 1024 bucket-и, 2 прогрівання і 5 вимірювань. На кожному вимірюванні паралельний індекс порівнювався з послідовним за document count і posting sets, включно з відсутнім терміном. Повні дані збережені у `benchmarks/results/2026-11-14/`.

Отримано (середній час у ms): для 500 документів sequential 61.072, pool 1/2/4/8 — 41.918/21.269/37.598/11.248; для 2000 — 122.958, 87.096/46.247/31.132/27.484; для 5000 — 268.567, 231.745/130.162/74.088/62.863; для 10000 — 501.394, 493.794/283.961/149.715/123.566. Найкращий результат цього запуску — 8 потоків на 500 документах (5.429×), але ефективність не є сталою; на 10000 документах 8 потоків дали 4.058× і 50.7% efficiency.

## Висновки

Власна структура даних і локальна синхронізація коректно підтримують конкурентне наповнення та читання. Власний pool забезпечує контроль життєвого циклу й скасування, а snapshot запобігає публікації часткового результату. Benchmark підтверджує залежність прискорення від розміру корпусу та кількості потоків: 2–4 потоки дали стабільні результати на великих корпусах, а надмірне збільшення пулу має накладні витрати. Перед здачею потрібно завершити Docker Compose та перевірити контейнерний сценарій на чистому клоні.
