# Процес розробки з використанням AI-агентів

## Джерела та межі підтвердження

Розробка виконувалася у взаємодії користувача з кореневим агентом Codex (`/root`). Локальний журнал `/Users/mac/.codex/history.jsonl` підтверджує 19 повідомлень, наведених дослівно у [ai-prompts.md](ai-prompts.md). Підлеглі агенти не залучалися. Цей опис не приписує агенту дій, яких немає у файлах, тестах або журналах.

## Етапи

1. **Аналіз вимог і структури.** Визначено межі курсової, наявні UML, backend, frontend і формат подальших етапів.
2. **Пошукове ядро.** Реалізовано власні `Document`, `Tokenizer`, `Bucket`, `TermEntry`, `PostingList`, `InvertedIndex`, послідовне та паралельне індексування.
3. **Паралелізм і надійність.** Перевірено розподіл документів, локальну синхронізацію bucket, snapshot-публікацію та власний `CustomThreadPool`; додано тести переривання, помилок і повторної побудови.
4. **Інтеграційні інтерфейси.** Додано REST API, Ollama query expansion із fallback, WebSocket-події, CLI та Web UI; їх контракти описані в README і перевіряються тестами.
5. **Діагностика середовища.** Виправлялися CORS, пошук датасету з різних робочих директорій і налаштування Docker/Ollama. Рішення приймалися після перевірки реальними запитами та логами.
6. **Вимірювання.** Проведено benchmark індексації та окремий throughput benchmark keyword-пошуку. Збережено raw CSV, summary CSV, environment metadata і SVG-графік; результати не замінювалися теоретичними оцінками.
7. **Фінальна перевірка.** Повторно запускалися Maven, CLI, frontend і benchmark-перевірки; Docker smoke-перевірка виконувалася окремо, коли Docker Engine був доступний.

## Роль людини

Користувач задавав вимоги, обмеження та порядок етапів, визначав, які компоненти не можна змінювати, і приймав рішення щодо публікації. Людина перевіряла логи, фактичні HTTP/WebSocket-відповіді, результати тестів і benchmark, вимагала пояснень для помилок, погоджувала Docker/Git-операції та визначала остаточний обсяг курсової. AI-агент готував зміни, тести й документацію, але не замінював перевірку результатів і не мав права вигадувати вимірювання.

## Перевірка і прийняття рішень

Кожний функціональний етап завершувався запуском відповідних тестів. Виявлені проблеми розглядалися за логами та відтворенням: зокрема, окремо перевірялися CORS, шлях UTF-8 датасету, таймаути Ollama і контейнерна адресація. Після змін повторювалися регресійні перевірки. Git commit/push виконувалися лише після явного дозволу користувача; документи про AI-промпти навмисно залишаються поза комітом для його перегляду.

## Що потрібно додати вручну

Для пояснювальної записки варто додати посилання на конкретні коміти/дати, скриншоти Web UI, повну конфігурацію апаратного середовища, якщо вона потрібна методичними вимогами, і власні висновки автора. Якщо університет вимагає повний експорт чату або формат цитування AI, його слід додати окремим додатком після перевірки політики закладу.
