# Послідовний індекс та уточнення UML

Історичний опис першого етапу. Потокобезпечну реалізацію та поточні контракти описано в [parallel-index.md](parallel-index.md). Нижче твердження про відсутність синхронізації стосуються лише першого етапу.

## Алгоритми

- Tokenizer: NFC, нижній регістр з Locale.ROOT, уніфікація апострофів, виділення Unicode літер/цифр із комбінованими знаками. Внутрішній апостроф зберігається; дефіс розділяє слова. Стемінг і стоп-слова не застосовуються.
- InvertedIndex: Bucket[] фіксованого розміру (типово 1024), позиція `floorMod(term.hashCode(), bucketCount)`. Це коректно і для Integer.MIN_VALUE.
- Bucket: ArrayList<TermEntry>, лінійне розв’язання колізій методом ланцюжків.
- TermEntry: термін і PostingList. PostingList зберігає відсортований ArrayList<String> без дублікатів. Пошук позиції O(log d), вставлення O(d) через зсув елементів.
- Пошук терміна: O(k) порівнянь у bucket; копіювання результату в TreeSet додає O(d log d). TreeSet використовується тільки для незалежної незмінної відповіді Set<String> за контрактом UML, не як основне сховище індексу. HashMap і ConcurrentHashMap не використовуються.
- Окремий список ID забезпечує підрахунок документів, зокрема порожніх. IndexBuilder відхиляє повторні ID та будує новий індекс, зберігаючи старий у разі помилки.

## Відповідність UML

Збережено Document (id/content/path і getters), InvertedIndex (addTerm/search/getDocumentCount), Bucket (insert/find), IndexBuilder.build(List<Document>), getLastBuildTime і getThreadCount.

Необхідні уточнення початкової діаграми класів:

1. Неописаний Entry конкретизовано як TermEntry; entries реалізовано дозволеним списком замість масиву. Додано PostingList.
2. Додано DatasetLoader, Tokenizer, registerDocument і getIndex. registerDocument потрібний для порожніх документів.
3. getLastBuildTime вимірюється в наносекундах. Читання датасету не входить у вимірювання.
4. ThreadPool, locks і setThreadCount належать наступному етапу. Поточна реалізація не потокобезпечна, getThreadCount завжди 1. Не можна одночасно будувати/змінювати та читати цей індекс.
5. Сигнатура buildIndex(N) із sequence diagrams не реалізована: поточний базовий контракт — build(documents), як у class diagram.

Оригінальні `.puml` і PNG залишено без змін: вони описують цільову систему. Перед паралельним етапом слід узгодити в них наведені контракти та стратегію синхронізації.

## Наступний етап

Додати Thread Pool і безпечну паралельну побудову, перевірити рівність індексів із послідовним варіантом, провести повторні вимірювання на більших корпусах. Лінійні вставлення posting lists та фіксована кількість buckets — свідомі обмеження базового варіанта, які потрібно враховувати в дослідженні.
